# `/docs/reference` — three files, each with a named consumer

**This folder no longer holds copies of documents that are replaced wholesale.** Seven were removed on 2026-08-08 by owner ruling, and the rule was sharpened the same day:

> **Repos keep no copies of documents replaced wholesale. A copy with a named consumer stays.**

**That is the test each file below passes**, and it is stricter than *"is this useful"* — a consumer has to be nameable.

| | What it is | Its consumer |
|---|---|---|
| `HouseSteady_Component-Types_config-v1.11.0.csv` | **Generated by this repo** — `server/scripts/component-types.ts` reads an export's config snapshot and writes it | Not a copy at all. Read by `walk-fixture.test.ts`; its canonical home *is* here, beside the script that makes it |
| `HouseSteady_Checklist-Master_v1-11.md` | The field app's checklist master, owner-authored, canonical in the field repo | **The schema cross-check, run by hand.** A doctrine scan requires it present; a second forbids any code path from reading it |
| `HouseSteady_Brand-Guide_v1_2026-07-17.html` | The brand's visual and voice reference, owner-authored, canonical in the project folder | **The report design.** Nothing parses it — the render carries its own tokens from `/brand/assets.json`, which cites this guide's §03 |

## Why the other seven went

The folder existed for a good reason that turned out to be wrong for one class of document.

**The reason:** handovers failed twice on documents that had gone stale in the project folder while the service moved underneath them. Keeping a copy here was meant to make staleness show up as a **diff** instead of as a wrong answer three weeks later.

**Why it failed for wholesale-replaced documents.** Such a copy goes stale the moment the source is recut, and **a stale copy looks exactly like a current one.** The Build Roadmap proved it inside twenty-four hours: it landed 2026-08-07 and was superseded 2026-08-08. Two of the nine copies were stale at the previous register cut and neither was noticed by anything here — they were caught by reading the register against the folder by hand, which is the work the folder was supposed to save.

**Why the rule kept an exception.** A document with a named consumer is not carried on the chance somebody reads it — something specific breaks without it. That makes its absence detectable, which is exactly what the seven lacked.

Removed 2026-08-08: Baseline Process · Baseline Service Design · Build Roadmap · Monthly Service Design · Plan v4 · Scope v4 · Scope Pending Changes. **Read them in the project folder.**

## Notes on the three that stayed

**The Component-Types CSV is regenerated, not maintained.** Increment 5 §1a requires every class's component type to be checked against **the import's own config snapshot**, never a list kept by hand:

```
npx tsx server/scripts/component-types.ts [manifest.json] [out.csv]
```

**The Checklist Master is bracketed by two doctrine scans**, and the pair is the point:

- *`is not read by any code path`* — nothing in `/server` or `/web` may parse it. Every import carries its own config snapshot, and component-name validation happens per import against that snapshot, failing open. A checked-in master would be a second authority that goes stale between field releases and produces confident wrong answers. **Not hypothetical:** running the cross-check by hand against a two-versions-stale config produced two false positives in one sitting, because `septic-alarm` was absent from the 48-type list only by being newer than it.
- *`is present, so the cross-check can be run by hand`* — it is here so somebody authoring the schema can check a name against the authority.

**The Brand Guide was removed on 2026-08-08 and restored the same day.** The removal read it as a project-folder copy like the others; the ruling is that it is owner-authored, outside the wholesale-replaced class, and has a consumer. **Restored.**

> ⚑ **And the flag it came back with is not the one that was expected.** The ruling asked that it be marked as needing a date, since *an undated file cannot show staleness as a diff.* **It carries one, in both places:** the filename is `_v1_2026-07-17`, and the document's own header line reads *HouseSteady · Brand Identity Guide · v1 · July 17, 2026*.
>
> **So the register's §2 row — `Brand Guide | undated | ○ △ | Undated, against rule 2` — does not describe this file.** Whatever is undated is the project folder's copy, and that is where the flag belongs. Reported rather than edited: §2 is the design session's section.
