# `/docs/reference` — two files, and neither is a carried copy

**This folder no longer holds copies of project-folder documents.** Eight were removed on 2026-08-08 by owner ruling: **repos stop keeping design-session copies at all.**

What remains is two files that are not copies of anything, plus this note.

| | What it is | Why it lives here |
|---|---|---|
| `HouseSteady_Component-Types_config-v1.11.0.csv` | **Generated by this repo** — `server/scripts/component-types.ts` reads an export's config snapshot and writes it | Not a copy. Its canonical home is here, beside the script that makes it |
| `HouseSteady_Checklist-Master_v1-11.md` | The field app's checklist master, owner-authored, canonical in the field repo | **A doctrine scan requires it to be present**, and a second scan forbids any code path from reading it. See below |

---

## Why the copies went

The folder existed for a good reason that turned out to be wrong.

**The reason:** handovers failed twice on documents that had gone stale in the project folder while the service moved underneath them. Keeping a copy here was meant to make staleness show up as a **diff** instead of as a wrong answer three weeks later.

**Why it failed.** The copy goes stale the moment the source is recut, and **a stale copy looks exactly like a current one.** The Build Roadmap proved it inside twenty-four hours: it landed on 2026-08-07 and was superseded on 2026-08-08. Nothing in the folder announced that. Two of the nine copies were stale at the last register cut and neither was noticed by anything here — they were caught by reading the register against the folder by hand, which is the work the folder was supposed to save.

**And the deeper problem is authority.** A Code session reading a document in this repo has no way to know whether it is current, and the register's rule already answers the question the folder was trying to: **a copy outside the canonical home is a copy, not a source.** The folder was an exception to that rule, kept for convenience, and it behaved the way exceptions to that rule behave.

**So the documents are read from the project folder, in session, at the time they are needed.** They are not carried, and they do not go stale here because they are not here.

---

## The two that stayed, and why each is different

**The Component-Types CSV is not a copy — this repo generates it.** Increment 5 §1a requires every class's component type to be checked against **the import's own config snapshot**, not a list kept by hand. The script reads a manifest and writes what that manifest says. The CSV is a working document for whoever is authoring the class list, and it is regenerated rather than maintained:

```
npx tsx server/scripts/component-types.ts [manifest.json] [out.csv]
```

**The Checklist Master is a copy, and it stayed on a recorded decision rather than by default.** Two doctrine scans bracket it:

- *`is not read by any code path`* — nothing in `/server` or `/web` may parse it. Every import carries its own config snapshot, and component-name validation happens per import against that snapshot, failing open. A checked-in master would be a second authority that goes stale between field releases and produces confident wrong answers. **That is not hypothetical:** running the cross-check by hand against a two-versions-stale config produced two false positives in one sitting, because `septic-alarm` was absent from the 48-type list only by being newer than it.
- *`is present, so the cross-check can be run by hand`* — it is here so somebody authoring the schema can check a name against the authority.

**If the ruling extends to this file too, the second scan comes out with it.** That is the owner's call and not a Code session's, so it is flagged here rather than decided. Note the same staleness risk applies: this copy is v1.11 and the field repo is the source.

## The rule that has not changed

**No Code session edits anything in this folder.** A change goes back through the owner and returns as a new dated file — the same rule the manifest contract already carries.
